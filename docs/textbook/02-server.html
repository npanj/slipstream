Request Lifecycle

POST /v1/chat/completionsentry
FrontendHandler.do_POST() parses the JSON body.
1 · Normalize shapeapi_shapes.py
OpenAI, Anthropic, or Responses shape → canonical messages.
2 · Prepare for generationfrontend.py
  • Jinja2 chat template → token ids
  • thinking.py: extract / encode thinking level
  • tool_schema.py: build tool-call grammar (CFG)
  • images.py: image → patch grid + digest
  • documents.py: PDF → text tokens
3 · Create Jobbackend.py
Assign priority + deadline. Priorities: foreground(0) / normal(1) / background(2).
4 · Write Request frame to piperuntime.py
If pending < pending_limit, write directly; else queue for the reader thread.
5 · Streamruntime.py → client
Read Tokens / MaskRequest / Done / Error frames from the pipe, project to SSE events, write to client.

The Subprocess Client runtime.py

  • Spawns the native binary (splash / slipstream)
  • Creates a pipe (os.pipe) → two fds
  • Reader thread: select() on the read fd, decode frames
  • Writer: non-blocking write of request frames
  • pending_limit: back-pressure; excess requests queue
  • CrashTraceRing: captures native crash backtrace
  • Callbacks run on the reader thread; blocking callers use RuntimeCall.result() on their own thread
Why a separate process? The native engine owns the GPU and the decode loop. Keeping it in its own process means a native crash is contained (captured by crash_trace.py) and the Python side can restart it, while the HTTP server and its in-process agent keep running.
