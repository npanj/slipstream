Layered Structure

MetalBuffer — Cheap Copyable References

MetalBuffer
A cheap, copyable reference to a backend-owned Metal allocation. Views keep the base allocation alive but do not increase the tracked allocation count — so a CommandGraph can hold many buffer views of one big allocation without confusing the memory ledger. Copy/assign are reference-counted; move is noexcept.

Allocation Failure Classification

Allocations return a classified AllocationResult, not a boolean. The engine's memory policy uses the class to decide between "wait for pressure to clear" and "this is a hard capacity wall":

FailureMeaningEngine response
Nonegrantedproceed
Capacityunclassified capacity refusal from an alternate backingretry with backoff
EngineBudgetexceeds the engine's own byte budget (governor reservation denied)reclaim within budget, retry
HostPressurehost memory pressure — the OS won't give us moresuspend work, reclaim, wait for pressure to clear
DriverRejectedthe driver/Metal refused the allocationfail the request (not retryable)

Command Submission

Build graphops → CommandGraph
The model's forward pass appends every dispatch (GEMM, attention, RoPE, sampling) to one CommandGraph. Param structs are memcpy'd into graph-owned storage at add() time — the graph is self-contained after building.
SubmitMetalBackend::submit(graph, completion)
Translates the dispatch list into a Metal command buffer: encodes each compute pass, binds buffers at their indices, binds the param struct as the final buffer. The completion callback fires on a GPU event when the buffer drains.
CompletionMetalEvent
The engine's pending_ ticket holds the completion. When it fires, FdTransport's control-wake wakes the loop, which calls Engine::tick() → apply(). Provisional writes (KV pages, state) become visible only after the command drains — this is what makes cancel/suspend safe mid-flight.
WatchdogCommandWatchdog
A command that doesn't complete within its timeout is a GPU hang. The watchdog surfaces it as a health failure → model_.checkHealth() fails all in-flight requests rather than letting the process wedge.

Device Capabilities

Capability queries
At startup, DeviceCapabilities queries the MTLDevice: max buffer count per dispatch, max threadgroups per grid, max threads per threadgroup, recommended max working set size, and unified-memory characteristics. These numbers drive the MemoryPlan (how big the KV pool can be) and validate that the planned dispatch geometries fit the hardware.
Pipeline cache
Pipeline states are compiled once (at warmup) and cached by kernel name. CommandGraph::add(pipeline, ...) takes a string name, not a pipeline object — the backend resolves name → MTLComputePipelineState at submit time. This keeps graphs serializable and cheap to copy around.

The ABI Boundary

abi/ — the C++ ↔ .metal contract
Every kernel's parameter struct is a plain C header (KernelABI.h family) included by both the C++ host and the .metal source. Requirements, enforced by static_assert on the C++ side:
  • std::is_standard_layout_v — C-compatible layout
  • std::is_trivially_copyable_v — memcpy'able into the param buffer
  • Fixed-size, no pointers into host memory (buffers are bound separately)

This is why a new kernel = one .h (ABI) + one .metal (implementation) + one ops builder (host). The model folder adds its own ABI headers for model-specific kernels (e.g. HyperConnection.h, DraftAttention.h).

Dependency rule: runtime/metal/ depends on nothing above it — no engine, no model, no ops. It is the foundation layer. The Backing interface in ops/PagedKv.hpp is the seam: the engine's KvPool implements it with Metal storage; tests implement it with deterministic host storage.
