Install & Launcher Python

Component deep-dive · Model discovery, download, path management, and process launching. Bridges the user-facing CLI to the native binary.

File Map

install/ ├── __init__.py package init ├── catalog.py official model catalog: bundled seed + refreshable cache ├── clients.py launch installed coding clients against a ready local server ├── launcher.py process launch: binary resolution, env, args ├── models.py model metadata, repo validation, download └── paths.py filesystem layout: models dir, runtime dir, venv, binaries

Path Layout

paths.py — where things live
PathSourceMeaning
MODELS$SLIPSTREAM_MODELS or ~/.slipstream/modelsDownloaded model weights
RUNTIMEDATA/runtime (packaged) or ROOT/build/runtime (dev)Runtime data (catalog cache, etc.)
PYTHONpython/bin/python3 (packaged) or .venv/bin/python (dev)Python interpreter for the server
BINARYfirst of: engine/slipstream, engine/slipstream-v2, engine/splashThe native engine binary

The PACKAGED flag switches between the installed-app layout and the source-tree layout. Binary resolution tries three names in order for backward compatibility.

Model Catalog

catalog.py — offline-safe discovery
Two sources, unioned:
SourceBehavior
Bundled seedVersioned with the source. Always present, always readable. Shell completion reads only this — it must never block and must work offline.
Refreshable cacheUnder the per-user data dir. Refreshed in the background by splash serve. A missing/stale/empty/corrupt cache can only fail to add entries — it can never remove a model the package already knew about.

This design means a bad network or a corrupt cache degrades gracefully: you always get at least the bundled models, and completion is never worse than a fresh install.

Launch Flow

splash servelauncher.py
  • Resolve the native binary (paths.BINARY)
  • Resolve the Python interpreter (paths.PYTHON)
  • Set env: model path, port, batch width, etc.
  • Launch the Python server, which in turn spawns the native engine as a child process
Model downloadmodels.py
Validate the repo id (validate_repo_id), download weights to MODELS/ if not present. The model folder layout must match what ModelFactory expects (manifest + weight files).
Client launchclients.py
Launch installed coding clients (e.g. a terminal agent) pointed at the ready local server. Connection/model config and safe launch defaults live here; tool inventories and prompts belong to the client, not Slipstream.

Process Tree

Three processes: the splash CLI (launcher) spawns the Python server, which spawns the native engine. The CLI exits after the server is ready (or stays as a supervisor, depending on the command). A coding client connects to the server over HTTP. The native engine is the only process that touches the GPU.
