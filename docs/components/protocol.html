The Wire Protocol v5

Component deep-dive · A binary frame protocol over a pipe. Python server/protocol.py and C++ runtime/engine/Protocol.cpp are mirror images of the same codec.

Frame Anatomy 24-byte header + payload

Key Payload Structures

Request
<Q B B B Q Q> head + <I I I f f I Q B> tail:
request id, priority, cohort, flags
prompt token count, deadline ms
max new tokens, temperature, topP, topK, seed
image span count, mask word count
followed by: token words, image spans, mask words
ImageSpan
<I I I I Q Q>:
offset, tokens, grid height, grid width
digest lo, digest hi (content identity)

Image pixels travel inside the request frame — a multi-image agent turn can carry well over 64 MiB of resized RGB bytes, hence the 256 MiB max payload.

Failure Model

FailureClass
PROTOCOL_FATAL — a framing/codec error; the stream is unrecoverable, the connection tears down.
REQUEST — one request rejected (bad params, over limit); other requests continue.
ENGINE — engine-internal failure surfaced to the request.
Truncation detection
The reader tracks how many header/payload bytes it has consumed. A stream that ends mid-frame reports exactly how many bytes of which frame type were read before EOF — e.g. "stream ended after 12 of 24 frame-header bytes" or "after 4096 of 8192 Tokens payload bytes". This is a terminal TRUNCATED_FRAME issue.
Why binary, not JSON: every token is a frame. JSON parsing on the hot path (per token, per request, at high concurrency) adds measurable latency and GC pressure. The 24-byte fixed header + typed payloads let both sides struct.unpack / memcpy with zero allocation for the common case. JSON is used only for the infrequent StatusJson snapshot.
