Shared Ops C++

Component deep-dive · Model-agnostic GPU operations. Shared ops/metal never depend on a model — they stay shared. Each op is a host-side builder that appends dispatches to a metal::CommandGraph.

Op Pattern

Every op follows the same shape: a host-side class that validates parameters, computes dispatch geometry (thread groups × threads), and appends to a CommandGraph. No op talks to Metal directly — that's the backend's job. No op knows which model is running.

Key Ops

PagedAttention
Three Q8 attention variants, each a validated params struct (standard-layout, trivially-copyable — static_asserted):
VariantUseKey params
Q8PrefillAttentionParamsfull prompt prefillrows, page table, physical page count
Q8ChunkedPrefillParamschunked prefill (long prompts)chunk stride, active rows
Q8VerifyAttentionParamsdraft verificationactive rows ≤ kQ8VerifyMaximumRows, splits ≤ kQ8VerifySplits

Validation is exhaustive: row ranges, stride alignment to kPageTokens, context bounds, page-table length, split counts. A bad param is a host-side error before dispatch, never a GPU fault.

PagedKv
The KV geometry contract shared with the engine's pool:
Backing interfacepage count, bytes/page, residency, extents, paced release
Q8Layout8-bit quantized KV: scales, head geometry, page token count
kMaximumLogicalTokenscontext ceiling = pages × pageTokens
pagesForAlignedMapping()sparse-mapping alignment math (gcd/lcm) for Metal buffer sizing
Sampling
Target sampling keeps kTargetSamplingCandidates = 32 top candidates per row (the protocol's MAX_TOP_K). Workspace is precomputed:
SamplingWorkspaceargmax values/indices, partial ids/values, top ids/probabilities
DraftSelectorWorkspacedraft candidate selection + proposal probabilities

SamplingPolicy { topK, temperature, topP, constrained } — constrained requests apply the CPU grammar mask before sampling.

RoPE
Generates cos/sine tables on the GPU:
addTables()target rows of (t, h, w) positions → cos/sin buffers
addDraftTables()draft rows of scalar positions → cos/sin buffers

Tables are computed per-batch into preallocated buffers, then consumed by the attention/GEMM dispatches in the same command graph.

Q8 KV Storage

Q8PageStorage
8-bit quantized KV pages: each page stores quantized K/V values + per-block scales. This is what makes long context affordable — Q8 KV is ~4× smaller than BF16, so the same physical memory holds 4× the context. The engine's KvPool manages which pages are resident; Q8PageStorage manages how bytes inside a page are laid out and read/written by the attention kernels.

Execution Plans

ops::ExecutionPlans
At startup, the model factory plans kernel dispatches for every shape it will use (max prefill, max decode width, verify rows, draft shapes). plannedRuntimeMemory() sums the scratch these plans need into the ModelMemoryPlan. At runtime, dispatches are replayed from the plan with per-batch parameter updates — no per-token kernel lookup or allocation. This is why warmup at maximum shapes matters: anything not planned is a cold path.
Dependency rule: ops depend on runtime/metal/ (CommandGraph, MetalBuffer, ABI headers) and runtime/model/ types (BatchPlan, ImageSpan). They never depend on runtime/engine/ or on a concrete model folder. Model-specific kernels (e.g. Qwen4 hyper-connection) live in the model folder, not here.
